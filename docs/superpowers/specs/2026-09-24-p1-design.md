## P1.1 — Content pipeline

**Source of truth: one JSON file per exercise in the repo**,
`content/exercises/<CODE>.json`, reviewed through normal PRs. The insert-only
seed stays for bootstrapping; a new sync command upserts reviewed content.

```json
{
  "code": "CP-004",
  "reference_solution": "def sum_to_n(n):\n    return sum(range(1, n + 1))",
  "tests": [
    {"description": "sums small n", "input": "sum_to_n(3)", "expected": "6",
     "category": "happy", "hidden": false},
    {"description": "zero", "input": "sum_to_n(0)", "expected": "0",
     "category": "boundary", "hidden": true}
  ],
  "mutants": [
    {"code": "...", "bug_line": 2, "bug_type": "off-by-one",
     "note_vi": "...", "note_en": "..."}
  ],
  "review": {"status": "draft", "author": "claude", "reviewer": null}
}
```

- Test categories: `happy` (typical), `boundary` (0, 1, empty, first/last,
  max), `edge` (negative, duplicates, None, unusual characters), `error`
  (only when the problem statement defines an error behaviour).
- Mutants: 3–5 per exercise, each a copy of the reference solution with exactly
  one line changed. They feed P2 (mutation testing and the new Ciel trap).

**Automatic validation (runs in the sandbox; also a pytest over every file):**
reference passes all tests; 1–2 visible + 5–8 hidden tests; hidden tests
cover `boundary` and `edge`; each mutant differs from the reference on
exactly `bug_line`, fails at least one test (killable) and passes at least one
(plausible); on debug-kind exercises the buggy starter fails at least one test.

**Review gate:** `sync --apply` only loads files with `review.status ==
"approved"` and a reviewer different from the author, and only if validation
passes. Reviewer checklist: `docs/content-authoring.md`.

**Leak guards (must ship before any hidden test reaches the DB):** exercise
detail lists visible tests only; `/run` executes visible tests only.

## P1.2 — Hidden tests at submit

- `/submit` runs the full suite (visible + hidden) on the latest snapshot and
  logs `SUBMIT_TESTS` {passRatio, visible/hidden passed/total, failed
  categories}.
- Submit response: counts plus the categories that failed (never inputs).
- Report / Feedback page: failing hidden inputs, expected and actual output.
- Testing axis stays interim until P2 (student-written tests) but switches
  from "last run, visible tests" to "submit, full suite".

## P1.3 — AHP weights and golden set (tooling + team work)

**AHP.** Each of the 4 members fills 15 pairwise comparisons of the 6 axes on
Saaty's 1–9 scale (a short form in the repo, one file per member, filled
independently). A script computes each member's priority vector (principal
eigenvector) and consistency ratio; anyone above CR 0.1 revises. Group weights
= aggregation of individual judgements by element-wise geometric mean (AIJ),
then eigenvector. Output: weights v1 + CR table, committed.

**Golden set.** 30–50 real sessions exported anonymised (no names/emails:
exercise, code snapshots, prompts and replies, hypothesis, explain-back
answers, run results). Each member rates every session independently with the
P1.4 rubric: per-axis level 0–3 (or N/A) and an overall holistic level. A
script computes inter-rater agreement (ICC for overall, weighted kappa per
axis) and engine-vs-human agreement.

Known limitation: the raters are also the builders, which biases toward the
engine's view. If a lecturer can rate even 15 sessions, include them.

## P1.4 — Rubric engine v2 (evidence-centred)

Each axis becomes 2–4 **observable indicators**, each scored at a level 0–3
with a written descriptor and the evidence that justifies it. Axis score =
20 × mean(indicator levels) / 3 over applicable indicators; N/A rules from P0
stay. The descriptors double as the golden-set rating guide, so humans and the
engine use the same scale.

Draft indicators (finalised in the P1.4 plan with the team):

| Axis | Indicators (evidence) |
|---|---|
| Understanding | explain-back correctness (LLM, anchored 0–3); read before acting (read ratio, first-prompt delay); no basic-concept asks to AI |
| Hypothesis | logged before code; judged correct; specificity: names approach and an edge case (LLM 0–3) |
| Prompting | per-prompt quality (LLM 0–3: context, specificity, constraint), averaged; no solution-begging (priming); no duplicate spam. A contextual, specific prompt must reach level 3 (= 20), fixing the P0 incentive |
| Verification | tested after AI code; caught the planted bug (from P0 events) |
| Testing | interim: submit-suite pass ratio mapped to levels |
| Debugging | from P0: fixed? efficiency (fails before fix) |

LLM judges (explain-back, hypothesis specificity, prompt quality) get anchored
rubrics with examples per level, JSON output with a level and a quoted
evidence span, temperature 0, and are validated against the golden set.
Levels shown to users: overall tier + per-axis level name; decimals hidden.

## P1.5 — Diagnosis + actionable feedback

- Diagnosis: deterministic **findings** from indicators, each with a code,
  axis, severity and evidence (event refs, code line, quoted answer).
- One LLM call at submit turns findings + problem + final code + reference
  solution + explain-back answers into JSON: per finding {what_happened,
  why_it_matters, how_to_improve, try_next (exercise code)}. It may only use
  the given findings (no invented critique); output validated; on failure or
  timeout, localized templates per finding code are used.
- Feedback carries codes and parameters, never English sentences for the
  frontend to regex.

## P1.6 — Frontend

Level display, the new per-finding feedback cards, hidden-test results on the
Feedback page, removal of regex note mapping. Separate plan in `codeprove-web`.

## P1.7 — Weight selection

With golden-set ratings and the v2 engine: compare AHP, equal, and
constrained-regression weights by agreement with human overall ratings
(Spearman and ICC, cross-validated because n is small). Prefer the simpler set
when differences are small. Commit the choice + evidence, then rescore.
