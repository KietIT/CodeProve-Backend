# P2 Design: New Exercise Mechanics

**Roadmap:** `docs/superpowers/specs/2026-09-24-scoring-roadmap.md`, section "P2 — New exercise mechanics".
**Status:** draft for the owner's review (2026-09-29). Nothing here is implemented until Kiệt approves this design and then each sub-phase plan.

## Why P2

P1 made the scoring evidence-based, but three axes still measure the wrong thing, because the exercises give the student no way to show the skill:

| Axis | What it measures today | Problem (evidence) |
|---|---|---|
| Testing | Pass ratio of the reference suite at submit (P1.2 interim) | Measures **correctness of the solution**, not whether the student can test. |
| Debugging | Failing runs before the fix, fixed or not at submit | On debug exercises the student just edits code like an implement exercise (owner test 2026-09-24); locating and explaining the bug are not observed. |
| Verification | How the student handled code in Ciel's replies (P1.4) | Observable in only **11/39** golden sessions (needs Ciel to give code); the "trap" is written by the LLM on the fly and can be harmless (P1.3, sim-02: the trapped code passed 8/8). |

Plus an integrity hole: asked point-blank, Ciel said it would not write the solution and then gave a nearly complete `two_sum`, which the student pasted and passed 8/8 (P1.3, sim-02). The rule lives only in the prompt.

## What P1 already provides

- **Content for all 30 exercises, approved** (`content/exercises/CP-*.json`): reference solution, 7–10 categorised tests (2 visible), and **108 validated mutants** (each a one-line change of the reference that at least one test kills and that does not fail every test), with `bug_line`, `bug_type`, `note_vi/en`.
- Full suite at submit with failures stored (P1.2); rubric engine v2 with levels and evidence (P1.4); diagnosis findings + templates (P1.5); Feedback page with levels, finding cards and hidden tests (P1.6).
- Sandbox: a test is a Python expression (`two_sum([3, 3], 6)`) evaluated against the code, compared by `repr` with the expected string.
- Frontend: the Daily Bug Hunt already has a clickable-line code view and a hint ladder.

## Sub-phases (in order)

```
P2.1 Ciel no-solution guard (code-enforced) ──────────────┐
P2.2 Debug mode: Locate → Fix + Debugging axis v3 ────────┤
P2.3 Tests tab: student tests + Testing axis v3 ──────────┤──► P2.6 Recalibration
P2.4 Verification review step (mutant bank, H − F) ───────┤     (golden set v2, rescore policy)
P2.5 Explain-back judge fixes (P1.5 findings) ────────────┘
```

Each sub-phase gets its own plan (backend here; frontend tasks handed to the CodeProve-UI session) and is approved before implementation. Order: P2.1 first because it closes a live integrity hole and is small; then the roadmap's [1] item (debug mode); then the [2] items.

### P2.1 Ciel no-solution guard

Before a Ciel reply is shown, the backend extracts its code blocks and runs them against the exercise's **visible** tests in the sandbox (the same check as a student run, a few hundred ms). If a block defines the exercise's entry point and passes all visible tests, the reply is withheld and replaced by guidance (a template plus the reply's prose without code). The event records `withheldSolution: true`; the prompt that caused it already carries `asks_for_solution` for the Prompting axis. Also applies to partial blocks that together pass (concatenate the blocks of one reply).

Not blocked: short snippets that do not pass (explanations, one-line examples), code the student pasted in the question.

**As built (2026-09-29, Kiệt asked for P2.1 first; threshold = decision 5 as proposed):** `app/features/mentor/guard.py`. A solving reply triggers one retry with a stricter instruction; if the retry also solves, the student gets a fixed bilingual message. Only the text the student saw goes to `PromptLog` (the Verification axis and the raters read it); `AI_REPLY.withheldSolution` records the block, and a withheld reply does not use up the exercise's trap. Hidden tests are not used (the check must not depend on what the student cannot see). Fails open (reply shown, warning logged) when the exercise has no visible tests or the sandbox errors. Cost: one sandbox run per reply that contains code; a withheld reply also costs one extra LLM call. No API or frontend change.

### P2.2 Debug exercise mode (the 9 debug exercises)

As in the roadmap's "Debug exercise mode":

1. **Locate.** The starter is read-only with clickable lines. The student selects the buggy line(s) and writes one sentence on why; optional hints (ladder: category of bug → region → line) lower the Locate indicator.
2. **Fix.** The editor unlocks; the student fixes, runs visible tests and submits (full suite, as now).

After submit, the real location and explanation are revealed on the Feedback page.

**Bug region** is derived, not entered: the lines where the effective starter and the reference solution differ (`difflib`), grouped into regions; exercises with several issues (CP-208) accept one selection per region. A content check (in `content.validate`) asserts every debug exercise has 1–3 regions of ≤ 3 lines.

**Debugging axis v3 for debug exercises** (implement exercises keep the P1.4 indicator):

| Indicator | Level 3 | 2 | 1 | 0 |
|---|---|---|---|---|
| Located | right region first try, no hint | right after 1 hint or 2nd try | right after 2+ hints | wrong / skipped |
| Explained | LLM judge: reason matches the real bug | partially | vague | wrong / empty |
| Fixed | full suite passes | visible pass, hidden fail | some visible fail | not fixed |
| Efficiency | 0–1 failing runs before the fix | 2–3 | ≥ 4 | — (only when fixed) |

Axis level = rounded mean of the applicable indicators (the P1.4 convention). New finding codes for P1.5 (`bug_not_located`, `bug_explained_well`, ...) with templates reviewed by the team as in P1.5.

### P2.3 Tests tab (student-written tests)

A tab next to the editor: a short explainer, a structured form per test (category: typical / boundary / edge / error; input expression; expected value; one line "why"), and a checklist ("at least one boundary case", ...). Fresher exercises get a learning mode: one worked example test pre-filled and hints on which categories are missing.

- **Live validity check** against the reference solution: the student learns only *valid / invalid* (plus the sandbox error for a syntax error), **never the reference's output**, so the tab cannot be used as an oracle for the answer. Rate-limited.
- **At submit:** each valid test also runs against the exercise's mutants; **mutation score** = killed mutants / mutants. Shown after submit with which mutants survived (their `note_vi/en`), not before.

**Testing axis v3:**

| Indicator | Evidence |
|---|---|
| Valid tests | share of the student's tests the reference passes |
| Category coverage | distinct categories among valid tests (vs the exercise's categories) |
| Mutation score | killed / total mutants at submit |

Correctness of the student's solution stays visible (hidden-test results, Debugging "Fixed") but **no longer drives Testing**. See decision 2.

### P2.4 Verification review step (replaces the LLM-written trap)

The roadmap's trap must be a validated mutant and scored by outcome (Youden H − F over buggy and correct items). Serving it **inside** the session conflicts with P2.1: a correct item would be the reference solution, which is the answer.

**Proposal:** a short **review step after the student's own submit, before explain-back**: "Ciel wrote this version; is it correct? If not, click the buggy line." 2 items per attempt, each either a random mutant (buggy, 40–70% of items overall) or the reference (correct); the student answers *correct* or picks a line. Scored per attempt with hits (buggy item, right line), misses and false alarms; the Verification axis becomes H − F mapped to levels, and it is **observable in every session** (today 11/39). The P1.4 indicator (how the student handled Ciel's real code during the session) stays as a second indicator when applicable. Reveal right after answering. Every Ciel code reply keeps the generic "AI can be wrong" note (already live).

The in-session LLM-written trap (`verification_trap` / `inject_error`) is removed.

### P2.5 Explain-back judge fixes

From the P1.5 review: the explain judge rated an explanation of buggy code as strong (a per-call `threading.Lock()`, items 3a/8b), and a question asked about a technique the student did not use (12a). Fixes: give the judge the full-suite result and the failing hidden tests, instruct it not to rate an explanation above level 1 when it explains code that the suite shows is wrong at that point; generate questions from the student's final code only. Validated on the golden sessions where it went wrong.

### P2.6 Recalibration

The new indicators change what Testing, Debugging and Verification mean, so the golden set needs sessions **with** the new evidence: simulate ~20 sessions through the new mechanics (the P1.3 simulator extended), the team rates them with an updated guide, agreement and engine-vs-human checked as in P1.4, weights re-checked with the P1.7 tool. Real sessions are added when they exist (P1.7 limitation).

**Old reports** have no Locate / student-test / review evidence: they keep their current scores (not rescored into the new axes); the Feedback page shows the axis as scored by the version in force at the time. The engine records `engine: "v3"` on new reports.

## Scoring and data changes (summary)

- New events: `LOCATE` (lines, reason, hints used), `STUDENT_TESTS` (tests + validity at submit), `MUTATION_RESULT`, `REVIEW_ANSWER`, `AI_REPLY.withheldSolution`.
- No new tables except possibly `student_tests` if tests must be editable across sessions (proposed: keep them in events, like everything else).
- Engine v3 = v2 + the new indicators; `SCORING_ENGINE=v3` switch as with v2.

## Decisions needed (before the sub-phase plans)

**Decided by Kiệt (2026-09-30):** 1 order as proposed; 2 = A (hidden-suite pass ratio as a fourth Testing indicator); 3 = A (Tests tab required on junior/senior, optional with learning mode on fresher); 4 = the post-submit "Review AI code" step; 5 = as proposed, built in P2.1; 6 = old reports keep their scores, no rescore into the new indicators.

1. **Order** P2.1 → P2.2 → P2.3 → P2.4 → P2.5 → P2.6 — proposed as above.
2. **Testing without correctness.** With Testing v3, a wrong solution with good tests can score well on Testing, and nothing else carries correctness except Debugging on debug exercises. Options: (A, proposed) add "hidden-suite pass ratio" as a fourth Testing indicator for implement exercises, weighted like the others; (B) a correctness multiplier on the overall; (C) accept it (correctness is shown, not scored).
3. **Tests tab required?** (A, proposed) Required on junior/senior (Testing is 0 without tests), optional with learning mode on fresher (Testing N/A without tests). (B) Optional everywhere.
4. **Verification review step** (P2.4) instead of an in-session trap: proposed yes, 2 items per attempt. Alternative: keep an in-session trap served only when the student asks for code, 100% buggy (no H − F possible).
5. **No-solution guard threshold:** withhold when a reply's code passes **all** visible tests (proposed) vs any code defining the entry point.
6. **Old reports** keep their scores, no v3 rescore (proposed).

## Out of scope

Tier cutoffs (P1.7 follow-up; needs real sessions), P3 (learner model, Ciel memory, RDS, privacy), AI-generated exercise variants.
