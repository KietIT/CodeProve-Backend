# P3 Design: AI Tutor + Infrastructure

**Roadmap:** `docs/superpowers/specs/2026-09-24-scoring-roadmap.md`, section "P3 — AI Tutor + infrastructure".
**Status:** draft for the owner's review (2026-09-30). Each sub-phase gets its own plan, approved before implementation.

## Where we start (checked 2026-09-30)

- **Ciel has no memory at all:** every message is sent with `history=[]`, so Ciel does not even see the previous question of the same attempt. It knows the exercise and the current code only.
- **Personalisation is static:** the P1.5 next-exercise `candidates()` picks unsolved exercises of the same or next level and category; nothing tracks what a student is good or weak at across exercises.
- **Exercises have** a level (fresher/junior/senior), a coarse `category` (Algorithms, Debugging, API security…), 3–5 mutants and categorised tests; no skill tags.
- **Every report stores** per-axis levels, evidence and findings (P1.4–P2.3): the raw material for a learner model.
- **LLM calls:** OpenAI chat completions, one model (`OPENAI_MODEL`), no per-user limit beyond the sandbox rate limit; `store` is not set (the API default is not to store).
- **Data:** Postgres in Docker on the EC2 host, daily `pg_dump` to S3; `events` is one table; no account deletion.

## Sub-phases (proposed order)

```
P3.1 Ciel remembers the attempt ─────────────┐ quick win, no new data
P3.2 Skill tags per exercise ──► P3.3 Learner model (Elo per skill) + learner brief
                                   ├──► P3.4 Next-exercise recommendation
                                   └──► P3.5 Ciel with the brief: scaffolded hints by level, progress report
P3.6 Cost controls (quotas, cache-friendly prompts, model tiering)
P3.7 Privacy (PII scrubbing, pseudonymisation, consent + opt-out, policy, PDPL review)
P3.8 Data infrastructure (account deletion API, retention, events partitioning, RDS)
P3.9 Periodic recalibration (process on real rated sessions)          (later) AI-generated exercise variants
```

### P3.1 Ciel remembers the attempt

Send the last N exchanges of the same attempt (from `PromptLog`, what the student saw) as chat history, capped by tokens. The P2.1/P2.2 guards run unchanged on each reply. Small, visible improvement; no new table.

### P3.2 Skill tags per exercise

A small fixed taxonomy (~15–20 tags, e.g. `hash-map`, `two-pointers`, `sliding-window`, `recursion`, `dynamic-programming`, `graph`, `off-by-one`, `null-handling`, `concurrency`, `input-validation`, `injection`, `error-handling`, `api-design`, `complexity`), 1–3 tags per exercise, in the reviewed content files (`skills` field, validated against the taxonomy), synced to the DB. The team reviews the taxonomy and the 30 assignments once.

### P3.3 Learner model and learner brief

- **Elo per skill:** each student has a rating per skill (start 1000); each exercise has a difficulty (start from its level: fresher 900, junior 1100, senior 1300). After a scored attempt, outcome = overall / 100 (a continuous Elo result); expected = 1 / (1 + 10^((D − R) / 400)); the student's rating moves on each tagged skill (K = 32), the exercise difficulty slowly (K = 8). Stored in a `learner_skills` table, recomputable from reports.
- **Axis profile:** a running mean of the six axis levels over the last attempts, plus the most frequent finding codes.
- **Learner brief:** a deterministic 150–300-token text (vi/en) built from those: strongest and weakest skills, axis trends, recurring issues. Never the full history, never code or chat text (privacy, cost).

### P3.4 Next-exercise recommendation

Replace the P1.5 `candidates()` and the dashboard suggestion with: among unsolved exercises, prefer those tagged with the student's weakest skills, with a predicted success probability near a target (≈ 0.7, from the Elo formula), not attempted recently. Same interface, so the Feedback page's "try next" keeps working.

### P3.5 Ciel with the learner brief

The brief goes into Ciel's system context (not the history). Hints scaffold by level (fresher: more concrete hints; senior: Socratic questions only). A progress report page (per student: skill ratings, axis trends, recent findings) built from the learner model; an optional short LLM summary of it.

### P3.6 Cost controls

Per-user quotas (Ciel messages per attempt and per day; clear message when reached), prompts laid out static-first so OpenAI's automatic prompt caching applies (system + exercise context before the per-message part), model tiering (a cheaper model for judges/validation if quality holds on the golden set). Monthly cost report from token counts already logged.

### P3.7 Privacy

PII scrubbing of student text before any LLM call (the export's email/phone scrubber, extended), pseudonymous user ids towards the LLM, `store=false` set explicitly, a privacy policy page, consent at sign-up and an opt-out of AI personalisation (no learner brief for those students). A PDPL (Decree 13/2023) legal review is a human task for the team.

### P3.8 Data infrastructure

Account deletion API (and data export for the student), a retention policy (e.g. raw events kept 12 months, reports kept), `events` partitioning by month when volume needs it, and the move to RDS (backups, point-in-time recovery; a cost decision).

### P3.9 Periodic recalibration

A documented routine: every N real rated sessions, rerun `analyze.py` and `weights.py` (P1.7) and review tier cutoffs (P1.7 follow-up). Needs the team to rate real sessions; also the natural place to finally run P2.6.

## Decisions needed

1. **Scope for the time available.** Proposed: P3.1 → P3.5 (the tutor part, most visible to students), then P3.6 quotas and P3.7 privacy basics (`store=false`, PII scrubbing, consent/opt-out); P3.8 and P3.9 later. Or another order.
2. **Skill taxonomy** of ~15–20 tags, 1–3 per exercise, reviewed once by the team (P3.2).
3. **Elo outcome = overall score / 100** (credits partial success) rather than solved / not solved.
4. **Ciel memory within an attempt:** last 6 exchanges (P3.1); across attempts only through the learner brief, never raw chat.
5. **Quota numbers** (P3.6), e.g. 30 Ciel messages per attempt and 100 per day — to confirm when that phase is planned.
